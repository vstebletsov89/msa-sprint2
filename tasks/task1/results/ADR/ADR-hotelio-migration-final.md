# Нефункциональные требования

| **№** | **Требование** |
| :-: | :- |
| 1 | **Поэтапная миграция**: переход на микросервисную архитектуру должен выполняться инкрементально, без Big Bang-переписывания и без остановки платформы. |
| 2 | **Масштабируемость**: наиболее нагруженный сценарий создания бронирования должен масштабироваться отдельно от остальных компонентов. |
| 3 | **Обратная совместимость API**: внешний REST API на переходном этапе должен сохраняться, чтобы клиенты и партнёрские каналы не меняли интеграцию. |
| 4 | **Независимость разработки**: разные команды должны иметь возможность разрабатывать, тестировать и выкатывать сервисы независимо. |
| 5 | **Локализация изменений**: изменение одного домена должно минимально влиять на остальные домены и не требовать знания всей кодовой базы. |
| 6 | **Разделение данных**: архитектура должна начать уход от shared database; каждый выделенный сервис должен получать собственное хранилище данных. |
| 7 | **Отказоустойчивость**: сбой одного сервиса не должен приводить к полной недоступности платформы; на межсервисных вызовах нужны timeout, retry и circuit breaker. |
| 8 | **Наблюдаемость**: архитектура должна подготавливать платформу к метрикам, централизованному логированию и распределённой трассировке. |
| 9 | **Подготовка к Kafka**: решение должно позволять публиковать события доменов и разгружать аналитические сценарии через асинхронную интеграцию. |
| 10 | **Подготовка к BFF / GraphQL**: архитектура должна поддерживать дальнейшее появление отдельного слоя для фронтенда. |
| 11 | **Ограниченность ресурсов**: миграция должна учитывать, что одновременно команда может качественно выносить не более 1–2 доменов. |
| 12 | **Скорость вывода новых фич**: после выноса домена новые изменения по нему не должны добавляться обратно в монолит. |
| 13 | **Подготовка к облаку**: разделение БД и сервисов должно облегчать будущий переезд инфраструктуры и rollout-практики. |
| 14 | **Безопасность взаимодействий**: в целевом состоянии межсервисные коммуникации должны поддерживать защищённые соединения и централизованные политики доступа. |

# Решение

## Анализ текущего состояния (As-Is)

Платформа Hotelio сейчас представляет собой Java-монолит, внутри которого сосуществуют пять доменных модулей: `BookingService`, `UserService`, `HotelService`, `PromoCodeService` и `ReviewService`. Все модули развёртываются единым артефактом и используют одну общую базу данных. Такая архитектура создаёт классическую связку из трёх проблем: высокая связанность бизнес-логики, невозможность точечного масштабирования и сложность независимой разработки.

Наиболее критичный бизнес-сценарий — создание бронирования. Именно он напрямую влияет на выручку и проходит через проверки нескольких доменов: пользователя, отеля, промокода и отзывов. Поэтому первый шаг миграции должен одновременно давать заметный бизнес-эффект и становиться шаблоном для следующих шагов.

## Выбор первого сервиса для миграции

В качестве первого кандидата рассмотрены все пять доменов.

| Кандидат | Бизнес-критичность | Нагрузка | Эффект от отдельного масштабирования | Сложность миграции | Итог |
|---|---:|---:|---:|-------------------:|---|
| BookingService | 5 | 5 | 5 |                  5 | **Выбран первым** |
| UserService | 3 | 2 | 2 |                  4 | Полезен, но слабый бизнес-эффект на первом этапе |
| HotelService | 4 | 3 | 3 |                  4 | Важен для поиска, но не снимает боль критического пути бронирования |
| PromoCodeService | 2 | 2 | 2 |                  4 | Прост в выносе, но почти не влияет на ключевые проблемы |
| ReviewService | 2 | 2 | 2 |                  4 | Низкий прямой эффект для основной выручки |

### Почему первым выносится BookingService

1. Это основной денежный сценарий платформы.
2. Он испытывает пиковую нагрузку и больше остальных выигрывает от независимого масштабирования.
3. Его вынос снижает связанность самого критичного процесса.
4. Он позволяет запустить Strangler Fig с максимальным видимым эффектом для бизнеса.
5. После его выделения можно запретить развитие booking-логики в монолите и ускорить дальнейшую декомпозицию.

## Целевой подход

Выбран паттерн **Strangler Fig**: монолит остаётся внешней точкой входа, а отдельные домены постепенно выносятся в независимые сервисы. На первом этапе монолит сохраняет внешний REST API, но часть вызовов проксируется в новый сервис бронирований.

### Промежуточное состояние на ближайшие месяцы

- внешний REST API по-прежнему обслуживается монолитом;
- создаётся отдельный `booking-service`;
- монолит перенаправляет создание и чтение бронирований в `booking-service`;
- `booking-service` получает собственную БД `booking-db`;
- на переходном этапе `booking-service` запрашивает данные пользователя, отеля, промокода и отзывов из монолита;
- после создания бронирования публикуется событие `BookingCreated` в Kafka;
- аналитика начинает читать данные не из боевой БД монолита, а из событийного/выделенного хранилища.

### Целевое состояние через год

- каждый домен работает как отдельный микросервис;
- у каждого сервиса собственная БД;
- фронтенд работает через GraphQL Gateway / BFF;
- Kafka используется как событийная шина;
- Service Mesh обеспечивает mTLS, traffic management и rollout-практики;
- observability реализована через метрики, логи и трассировку.

## Обоснование ключевых архитектурных решений

### 1. Strangler Fig вместо Big Bang

Переход выполняется постепенно, чтобы не останавливать бизнес и не пытаться переписать весь монолит сразу. Это уменьшает риск, сохраняет работающий продукт и позволяет проверять паритет поведения регрессионными тестами на каждом этапе.

### 2. Выделение BookingService как первого домена

BookingService находится в самом центре бизнес-ценности и сильнее остальных выигрывает от отдельного масштабирования. Это не самый простой кандидат, но самый выгодный по соотношению «сложность / эффект».

### 3. Собственная БД для booking-service

Разделение данных начинается с самого нагруженного домена. Это одновременно снимает часть нагрузки с общей БД и вводит правильную модель ownership data по сервисам.

### 4. Синхронные вызовы к монолиту на переходном этапе

До миграции остальных доменов новый `booking-service` использует монолит как источник данных по пользователям, отелям, промокодам и отзывам. Это позволяет избежать дублирования логики и ускоряет первый этап миграции. Зависимость от монолита считается временной и устраняется по мере выноса остальных сервисов.

### 5. Kafka для событий бронирования

События бронирования полезны для аналитики, нотификаций и дальнейшего масштабирования интеграций. Асинхронная публикация через Kafka разгружает основную БД и создаёт задел под событийную архитектуру.

### 6. BFF / GraphQL не на первом этапе

Проблема фронтенда признаётся архитектурно значимой, но её решение откладывается до момента, когда появится достаточное число независимых сервисов. На раннем этапе главная цель — декомпозиция критического пути бронирования.

## Пошаговый план миграции

### Фаза 1. Подготовка
1. Запустить приложение и БД.
2. Выполнить тесты и зафиксировать baseline в `test-log.txt`.
3. Зафиксировать текущие API-контракты и регрессионное поведение.
4. Подготовить инфраструктуру для нового сервиса и отдельной БД.

### Фаза 2. Выделение BookingService
1. Создать новый `booking-service`.
2. Перенести в него бизнес-логику создания бронирования.
3. Создать `booking-db`.
4. Настроить проксирование запросов из монолита в новый сервис.
5. Сначала перевести `POST /bookings`, затем чтение бронирований.
6. Запустить контрактные и регрессионные тесты.

### Фаза 3. Событийная интеграция
1. Публиковать `BookingCreated` после успешного создания бронирования.
2. Подключить consumer для истории и аналитики.
3. Убрать аналитическую нагрузку с боевой БД.

### Фаза 4. Дальнейшая декомпозиция
1. Выделить `UserService`.
2. Выделить `HotelService`.
3. Выделить `PromoCodeService`.
4. Выделить `ReviewService`.
5. Постепенно заменить вызовы `booking-service -> монолит` на вызовы к отдельным сервисам.

### Фаза 5. Финализация архитектуры
1. Добавить GraphQL Gateway / BFF.
2. Ввести Service Mesh.
3. Стандартизировать rollout-стратегии и наблюдаемость.
4. Вывести остаточную booking-логику из монолита.

# Альтернативы

## Альтернатива 1: Big Bang Migration

**Описание:** Полностью переписать систему и одномоментно перейти на микросервисную архитектуру.

**Причины отклонения:**
- слишком высокий риск для бизнеса;
- долгий срок до первой поставки результата;
- высокая вероятность расхождения с текущим поведением системы;
- ограниченные ресурсы команды делают подход нереалистичным.

## Альтернатива 2: Начать с простого сервиса

**Описание:** Сначала вынести `PromoCodeService` или `ReviewService`, потому что они проще.

**Причины отклонения:**
- слабый бизнес-эффект на первом этапе;
- практически не решает проблему масштабирования критического пути;
- даёт меньше организационного эффекта для команд.

## Альтернатива 3: Сначала внедрить BFF / GraphQL

**Описание:** Сначала построить новый фронтенд-слой и только потом мигрировать домены.

**Причины отклонения:**
- не решает главную проблему монолита;
- добавляет ещё один слой поверх существующей связной системы;
- эффективнее внедрять после появления независимых сервисов.

**Недостатки, ограничения, риски**

### Недостатки выбранного решения

1. На переходном этапе появляется распределённая система со всеми её издержками: сетевые ошибки, таймауты, ретраи и более сложная отладка.
2. Новый `booking-service` первое время остаётся зависимым от монолита, поэтому полная автономность достигается не сразу.
3. Разделение данных усложняет миграцию и требует внимательной стратегии cut-over.

### Ограничения

1. Команда ограничена в ресурсах, поэтому параллельно мигрируются не более 1–2 доменов.
2. На переходном этапе внешний API нельзя ломать.
3. Полный отказ от общей БД достигается только в несколько шагов, а не сразу.
4. Новые фичи по уже выделенному домену должны идти только в новый сервис, иначе миграция будет «откатываться назад».

### Таблица рисков

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Рассинхронизация данных при переносе бронирований в `booking-db` | Средняя | Высокое | Пошаговая миграция данных, backup, shadow write / сверка до переключения |
| Рост latency из-за цепочки межсервисных вызовов | Средняя | Среднее | Параллелизация независимых проверок, timeout, retry, circuit breaker |
| Недоступность монолита влияет на `booking-service` | Средняя | Высокое | Минимизировать время переходного этапа, использовать graceful degradation там, где возможно |
| Ошибка маршрутизации/проксирования ломает внешний сценарий бронирования | Средняя | Высокое | Контрактные тесты, feature toggle, постепенное включение |
| Потеря событий при публикации в Kafka | Низкая | Среднее | Transactional Outbox, idempotent consumer, retry |
| Команда не успевает мигрировать несколько доменов параллельно | Высокая | Среднее | Жёстко ограничить WIP, мигрировать по одному критичному домену |
| Возврат новой booking-логики в монолит | Средняя | Среднее | Зафиксировать архитектурное правило: все новые фичи booking только в `booking-service` |

# Итог

Для Hotelio выбран инкрементальный переход от монолита к микросервисной архитектуре по паттерну Strangler Fig. Первым выделяется `BookingService`, так как он лучше остальных сочетает бизнес-критичность, нагрузку и эффект от отдельного масштабирования. Решение даёт быстрый практический результат, не ломает внешний API и создаёт устойчивую основу для дальнейшего выделения доменов, разделения БД, внедрения Kafka, observability и GraphQL/BFF.
